Live Analytics

2026
  • Mathematics
  • Data Science
  • Python
  • Ultralytics YOLO
  • Supervision
  • OpenCV
  • Scikit-Learn
  • RoboFlow

Building on the ideas used in my prediction model, I thought it would be a good idea to potentially resolve some of the data limitations by building my own live pipeline. The idea is to track all the things that a static scrape from a website could not generate, like individual player stats and how game statistics change over time. Following the tutorial by Code in a Jiffy was a good starting point and if I wanted to further develop this, I could implement the same ideas as the Roboflow YouTube channel used for their basketball analytics.

Using footage from a local match and an additional data set from Roboflow I started the training using the YOLOv5xu model through my GPU. To track a player on each input frame we needed to create bounding boxes around them. This bounding box would then later be replaced with an ellipse around the players feet to make it more visually appealing. To perform this tracking ByteTrack was used and not DeepSORT. ByteTrack associates each detection, even low confidence ones, to existing tracks instead of discarding them. In football there is a lot of overlap of players, DeepSORT relies on appearance features to re-associate the tracks, which adds latency and complexity. ByteTrack achieves better tracking accuracy through IoU, making it simpler to deploy for this test run.

To assign the teams we made use of clustering. For this project we used KMeans to detect the colors of the two teams. We used the top half of the player and converted it to a 2D image to train the clustering model. We looked at the 4 corners of the image using it as the background, leaving the other color as the team color. By using KMeans and setting k equal to 2, we are easily able to separate the two dominant colors which will be the background grass for example and the jersey color. This is computational cheap and does not require labelled data.

The next area to tackle was the camera movement, perspective, and how to deal with the model not being able to identify the ball. For the camera movement, points needed to be fixed on the field so that if the camera moves the input should not be taken as actual movement. The same goes for the perspective. To accurately read the speed statistics of a player, the perspective of the camera needed to be considered. To do this we mapped points from one plane to another using a homography matrix. We take four known trapezoid points on the pitch and four destination points. The last thing we used here was the ball interpolation. In case the model was not able to follow the ball anymore we made use of interpolation where we assumed that the ball will continue traveling in its last known direction and the bounding box closest to that line should receive the ball. Obviously this is not a perfect solution and can be improved on.

Limitations & Improvements

Because the ball interpolation is not the best way to solve this issue, we can make use of what the Roboflow channel uses in their NBA example and create a separate CV model that is only focused on the ball. The speed readings are also inaccurate and have been removed from the current output as the perspective transform vertices are hardcoded. Ideally we would replace them with pitch keypoints that recompute them each frame. Occasionally a player gets assigned to the wrong team. To attack this we could use the KMeans clustering on several frames instead of just one and handle goal keepers separately.
